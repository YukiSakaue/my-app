# チーム向けタスク管理アプリ 仕様

## 0. このドキュメントの扱い

これは実装の仕様書です。着手前にこのファイル全体を読み、**実装計画を提示して承認を待ってください**。
勝手に全フェーズを一気に実装しないこと。フェーズ単位で進め、各フェーズ完了時にコミットして報告してください。

## 1. 目的

小規模チーム（5〜20人程度）が使うタスク管理ツール。以下の3点が中核。

1. リーダーがメンバーにタスクを割り振る
2. 各タスクの進捗状況を記録・閲覧する
3. 各タスクに取り組んだ時間を記録・閲覧する

「多機能にすること」より「この3点が確実に動くこと」を優先する。

## 2. 技術スタック（確定。勝手に変更しない）

- Node.js LTS / Express
- PostgreSQL、クライアントは `pg`（ORM は使わない。SQL は自分で書く）
- マイグレーション: `node-pg-migrate`
- 認証: bcrypt でパスワードハッシュ、JWT を httpOnly Cookie に格納
- 画面: EJS によるサーバーサイドレンダリング + 必要最小限の素の JavaScript
  （SPA にはしない。単一の Web サービスとしてデプロイするため）
- テスト: `node:test` + `supertest`
- 設定はすべて環境変数から読む: `DATABASE_URL`, `PORT`, `JWT_SECRET`

### デプロイ制約（Render）

- `app.listen(process.env.PORT || 3000, '0.0.0.0')` とすること。ポートのハードコード禁止
- 秘密情報は `.env` に置き、`.env` は `.gitignore` に含める。`.env.example` は commit する
- `package.json` に `engines.node` を書き、`package-lock.json` を commit する
- npm scripts: `dev` / `start` / `migrate` / `test`

## 3. データモデル

以下のテーブルを作る。カラム名・型が妥当でない箇所があれば、実装前に指摘すること。

- `users` — id, name, email(unique), password_hash, created_at
- `teams` — id, name, created_at
- `team_members` — team_id, user_id, role(`leader` | `member`), joined_at
  （複合主キー。1人が複数チームに所属でき、チームごとに role を持つ）
- `tasks` — id, team_id, title, description, assignee_id(nullable), created_by,
  status, due_date(nullable), estimated_minutes(nullable), created_at, updated_at
- `task_status_history` — id, task_id, from_status, to_status, changed_by, changed_at
- `time_entries` — id, task_id, user_id, started_at, ended_at(nullable),
  minutes(int), note(nullable), created_at

補足:

- `status` は `todo` / `in_progress` / `review` / `done` の 4 値。DB 側で CHECK 制約か enum を使う
- 作業時間は **分単位の整数** で保持する。浮動小数を使わない
- `time_entries.ended_at` が NULL のレコードは「計測中」を意味する。
  1ユーザーにつき計測中レコードは同時に1件までとし、DB の部分ユニークインデックスで保証する
- 日時は UTC で保存し、表示時に JST へ変換する
- 外部キーには適切な ON DELETE を設定する（タスク削除で time_entries が孤立しないこと）

## 4. 権限

| 操作 | leader | member |
| --- | --- | --- |
| タスクの作成・編集・削除 | ○ | × |
| タスクの割り当て・再割り当て | ○ | × |
| 自分に割り当てられたタスクのステータス変更 | ○ | ○ |
| 自分の作業時間の記録・編集・削除 | ○ | ○ |
| 他人の作業時間の編集 | × | × |
| チーム全体のタスク・集計の閲覧 | ○ | ○ |
| メンバーの招待・role 変更 | ○ | × |

権限チェックは Express のミドルウェアに集約し、各ルートハンドラに散らさないこと。
所属していないチームのデータには一切アクセスできないこと（テストで確認する）。

## 5. 機能要件

### 5.1 認証

- サインアップ / ログイン / ログアウト
- パスワードは 8 文字以上。ハッシュ化して保存する

### 5.2 チーム

- チーム作成（作成者が自動的に leader になる）
- 招待コードまたはメールアドレス指定でメンバー追加
- メンバー一覧、role 変更

### 5.3 タスク

- リーダーによる作成（タイトル、説明、担当者、期限、見積時間）
- 一覧: ステータス別 / 担当者別 / 期限順で絞り込み・並べ替えができること
- 詳細画面: 基本情報、ステータス変更履歴、その タスクの作業時間ログ、合計時間
- ステータス変更時は必ず `task_status_history` に記録する

### 5.4 作業時間

2 通りの記録方法を両方サポートする。

- **タイマー**: タスク詳細で「開始」→ `time_entries` を ended_at=NULL で作成。
  「停止」で ended_at と minutes を確定。計測中は画面上部に常時表示する
- **手入力**: 日付・作業時間（分）・メモを直接登録・編集・削除する

### 5.5 閲覧・集計

- **チームダッシュボード**: メンバーごとの担当タスク数、ステータス内訳、今週の合計作業時間
- **タスク別集計**: 見積時間 vs 実績時間
- **個人ビュー**: 自分の担当タスクと、直近 30 日の作業時間推移

集計は SQL の集約関数で行う。アプリ側で全件取得してから JS で集計しないこと。

## 6. 進め方（フェーズ）

各フェーズは「実装 → テスト作成・通過 → コミット → 報告」で1区切り。
承認を得てから次のフェーズに進むこと。

1. プロジェクト雛形、DB 接続、マイグレーション基盤、ヘルスチェック `/healthz`
2. 認証（サインアップ / ログイン / ログアウト）と認証ミドルウェア
3. チームとメンバー管理、権限ミドルウェア
4. タスク CRUD、割り当て、ステータス変更と履歴
5. 作業時間（タイマー + 手入力）
6. ダッシュボードと集計ビュー
7. Render 用の `render.yaml` と README（ローカル起動手順・デプロイ手順）

## 7. 品質基準

- 権限まわりは必ずテストを書く。「他チームのタスクが見えない」「member がタスクを削除できない」を明示的に検証する
- SQL は必ずプレースホルダを使う。文字列結合でクエリを組み立てない
- エラーは握りつぶさず、ユーザーに表示するメッセージと、ログに出す詳細を分ける
- 1ファイル 300 行を超えそうなら分割する
